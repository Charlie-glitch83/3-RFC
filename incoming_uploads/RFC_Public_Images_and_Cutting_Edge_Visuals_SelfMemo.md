## 0. Executive instruction to myself

The next RFC preprint needs to look like a serious physics/cosmology paper, not like an AI-generated manifesto and not like a generic LaTeX dump. The visual system must do three jobs at once:

1. **Make the triadic scientific structure legible.** The reader should understand that CIF/QV/RFL is being translated into scientific roles: latent state space, compression/selection dynamics, and realized geometric/observable structure.
2. **Make the no-retune module architecture credible.** The paper must show dependency order visually: canonical source material -> deterministic closure -> frozen packet -> audit modules -> external boundary ledgers.
3. **Make the paper visually memorable without weakening scientific trust.** “Bad ass” means precise, cinematic, high-contrast, clean, and data-driven. It does **not** mean cluttered, mystical, over-saturated, or filled with decorative space art.

The safest design rule is:

> Use public images sparingly as atmospheric section openers or contextual plates; use original vector diagrams, data-driven figures, and source-audit tables as the scientific core.

The strongest final visual identity should combine:

- a small number of carefully credited public-domain or Creative Commons cosmic images;
- original RFC-specific diagrams generated from the project sources;
- code-generated plots from frozen packets and ledger outputs;
- a strict claim-boundary visual language; and
- a polished PDF layout that uses vector graphics wherever possible.

## 1. Public-image licensing doctrine

### 1.1 Preferred licensing hierarchy

For a scientific preprint, use images in this order of preference:

1. **Original figures created from RFC data/code.** Best option. No external license complications. Maximum scientific relevance.
2. **NASA public-domain or generally copyright-free educational/editorial images.** Strong option, but check individual pages for third-party marks and credits.
3. **ESO images under CC BY 4.0.** Strong option if credit is clear and visible.
4. **Wikimedia Commons files with explicit public-domain, CC BY, or CC BY-SA license.** Use only after verifying the file page, author, source, license, and derivative obligations.
5. **ESA images.** Use carefully. ESA pages vary. Prefer Planck images mirrored or explained on NASA pages when possible, while still crediting ESA/Planck Collaboration.
6. **APOD images.** Use carefully. APOD features many images, but each has its own credit; APOD does not automatically mean NASA public domain.
7. **Stock images or AI-generated cosmic art.** Avoid for the preprint unless there is a compelling cover-only reason and license is crystal clear. These weaken scientific authority.

### 1.2 NASA image-use facts to remember

NASA’s own usage guidance says NASA content — including images, audio, video, and certain 3D model media — generally is not subject to copyright in the United States and may be used for educational or informational purposes. NASA also says factual use that does not imply endorsement usually does not require explicit permission, but NASA should be acknowledged as the source. However, NASA warns that some images on its sites may contain third-party copyrighted material, and those must be treated separately. NASA also restricts use of its logo, insignia, identifiers, and endorsements.

**Use in preprint:**

- Acceptable: NASA CMB image page, NASA Webb/Hubble pages, NASA Visible Earth, NASA SVS visualizations, NASA APOD entries when the credit/license is verified.
- Avoid: NASA logo as decoration, NASA “approval” language, NASA employee/astronaut likenesses where publicity rights are involved, third-party images hosted on NASA pages without rights clearance.
- Caption style: “Image credit: NASA/ESA/Planck Collaboration” or the exact source credit from the page.

**Primary source:** NASA Images and Media Guidelines: https://www.nasa.gov/nasa-brand-center/images-and-media/

### 1.3 ESO image-use facts to remember

ESO’s copyright notice says that, unless specifically noted, images, videos, music distributed on the public ESO website, and certain public texts/captions are under Creative Commons Attribution 4.0 International License. The key condition is clear and visible credit; ESO explicitly says credit must not be hidden or separated from the image.

**Use in preprint:**

- Very good for cosmic web imagery and telescope-related images.
- Use exact credit line from image page.
- Include license note in figure caption or image-credit table: “ESO material licensed CC BY 4.0 unless otherwise noted.”
- Do not use ESO logo except as permitted.

**Primary source:** ESO Copyright Notice: https://www.eso.org/public/outreach/copyright/

### 1.4 Wikimedia Commons reuse doctrine

Wikimedia Commons is useful but must be treated like a license registry, not a source of automatic permission. Commons says almost all content may be freely reused subject to the relevant license restrictions, but each file can have different requirements, including attribution, license links, ShareAlike obligations, or derivative-license obligations. Commons explicitly advises verifying licensing and facts for each file.

**Use in preprint:**

- Do not cite “Wikimedia Commons” alone as the image creator.
- Use the original author/source listed on the file page.
- Prefer public-domain NASA/Hubble files or CC BY files over CC BY-SA if the paper might be republished in a context that dislikes ShareAlike requirements.
- Avoid “fair use” files. They are not suitable for broad preprint reuse.

**Primary source:** Commons reuse guide: https://commons.wikimedia.org/wiki/Commons:Reusing_content_outside_Wikimedia

## 3. What public images should actually be used?

### 3.1 Use only the images that strengthen scientific flow

The paper should not become an image scrapbook. The best public-image set is probably:

1. **Planck CMB map** — empirical early-universe context.
2. **Cosmic web simulation** — large-scale structure/RFL context.
3. **Optional Hubble/Webb deep-space image** — cover or section opener only.
4. **Optional gravitational-wave spectrogram inspiration** — but preferably recreate from open data or schematic code.

Everything else should be original.

### 3.2 Avoid public images for RFC-specific claims

Do not use external images to claim that RFC is validated. The visual grammar must say:

- “This is the empirical phenomenon/domain RFC wants to project toward.”
- “This is the RFC internal structure.”
- “This is the boundary status of the claim.”

Public images provide **domain context**. Original diagrams provide **model content**.

### 3.3 External-image caption rule

Every external-image caption must include:

- what the image is;
- whether it is observation, simulation, or illustration;
- why it appears in the paper;
- what RFC does and does not claim from it;
- exact credit;
- license note if required.

Never let a public image do argumentative work by implication.

## 5. Cutting-edge graph and chart types to use

### 5.1 Dependency DAGs

Use for:

- source precedence;
- no-retune chain;
- module dependencies;
- theorem/boundary relationships.

**Recommended toolchain:** Graphviz, Mermaid for drafts, then redraw in SVG/PDF with Illustrator/Inkscape or use `graphviz`/`networkx` export.

**Design advice:**

- Use strict hierarchy.
- Avoid hairball networks.
- Use clusters: canonical sources, closure modules, boundary ledgers, external data.
- Edge labels should be verbs: “defines,” “freezes,” “audits,” “projects,” “tests.”

### 5.2 Sankey/alluvial diagrams

Use for:

- P25 modules -> ZIP upgrade lanes -> claim statuses;
- source files -> preprint sections;
- triad components -> mathematical roles -> observables.

**Recommended toolchain:** Plotly for initial layout, then export as SVG/PDF and clean manually if necessary.

**Design advice:**

- Keep under 30 flows.
- Use subdued colors.
- Make all nodes readable in grayscale.

### 5.3 Matrix heatmaps

Use for:

- module-by-triad role mapping;
- claim-boundary status;
- source-data map;
- internal/external validation readiness.

**Recommended toolchain:** Matplotlib, seaborn only if used carefully, or custom Matplotlib for publication control. For the final paper, prefer Matplotlib with explicit typography and cell labels.

**Design advice:**

- Do not use rainbow.
- Use one perceptually uniform palette.
- Use annotations for exact values only when the matrix is small enough.
- Include column groups and row groups.

### 5.4 Small multiples

Use for:

- kernel contribution layers;
- downstream module outputs;
- boundary lane comparisons;
- before/after P25 vs ZIP improvement.

**Design advice:**

- Same axes whenever comparison matters.
- Titles should state the role, not just the variable name.
- Use thin reference lines and minimal grid.

### 5.5 Phase-space plots

Use for:

- collapse/rebirth dynamics;
- attractor convergence;
- bifurcation and recursive memory;
- observer divergence.

**Design advice:**

- A phase-space figure can be visually stunning, but must be explained carefully.
- Use annotations for attractor, bifurcation, and stable/unstable regions.
- Do not overplot unless using alpha blending or density contours.

### 5.6 Bifurcation diagrams

Use for:

- Feigenbaum/recursive scaling.

**Best approach:** generate original high-resolution plot from code.

**Design:**

- Black or off-white background depending on section.
- Use millions of points if needed, but export as high-resolution raster if vector becomes too large.
- Add minimal annotations: period-doubling, onset of chaos, Feigenbaum scaling marker.

### 5.7 Spectrograms / chirp plates

Use for:

- gravitational-wave boundary modules;
- signal/frequency-time metaphors only where physically appropriate.

**Best approach:** recreate from open GW data or synthetic demonstration, clearly labeled. Do not embed APOD graphic unless rights are verified.

### 5.8 Ternary plots

Use for:

- triad composition: CIF/QV/RFL fractions;
- Module R group power distribution;
- source-coupling balance.

**Design:**

- Ternary plots look advanced and are conceptually perfect for triadic theory.
- Use sparingly; many readers are unfamiliar with them.
- Always include a plain-language caption and perhaps an inset stacked bar.

### 5.9 Ridgeline / waterfall plots

Use for:

- recursive levels `n` or `j`;
- kernel layer evolution;
- closure metrics across module family.

**Design:**

- Works well for showing recursive depth.
- Avoid if it becomes decorative instead of quantitative.

### 5.10 “Spec sheet” parameter tables

Use for:

- frozen packet;
- module statuses;
- public-data handoff.

**Design:**

- Use cards, not spreadsheet walls.
- Group related quantities.
- Include units/status/claim boundary.
- Put exact values in a monospace column.

## 6. Table design doctrine

### 6.1 Tables should become visual instruments

The next paper needs several tables, but not dull ones. The tables should be engineered as scientific instruments:

- **Table 1:** Triad scientific translation. CIF/QV/RFL -> mathematical role -> observable role -> blocked metaphysical language.
- **Table 2:** Canonical source precedence. P24/P25/P26/P27/ZIPs -> use in new preprint -> authority level.
- **Table 3:** Frozen packet. Parameter -> value -> derivation/source -> downstream role.
- **Table 4:** Module upgrade map. P25 module -> ZIP lane -> improvement -> claim status.
- **Table 5:** Boundary ledger. Domain -> internal status -> external data needed -> blocked claims.
- **Table 6:** Figure source/credit ledger. Figure -> source -> license -> credit -> modification status.
- **Table 7:** Public-data handoff. Dataset -> module -> intended test -> no-retune constraint.

### 6.2 Table layout rules

- Use short row labels.
- Put long explanations in notes, not inside cells.
- Avoid vertical lines.
- Use alternating light row shading only if it improves scanning.
- Use small status chips: `internal`, `proxy`, `external`, `blocked`.
- Use one consistent table grammar across the paper.
- Every table should answer one question.

### 6.3 Best table style for PDF

For a LaTeX/PDF manuscript:

- Use `booktabs` style rules.
- Use `tabularx` or `longtable` for wider tables.
- Use `threeparttable` for notes.
- Use `siunitx` for aligned numeric columns.
- Use landscape pages only for supplementary tables, not main text.
- For visually rich status matrices, create them as vector figures, not LaTeX tables.

## 7. Color system for the RFC preprint

### 7.1 Do not use arbitrary mystical colors

The old triad could tempt us into symbolic color overuse. Avoid that. The scientific preprint should use color as a functional encoding system.

### 7.2 Proposed triad palette

A polished palette could use:

- **CIF:** deep violet / electric indigo — state space, modal possibility.
- **QV:** black-blue / dark graphite — compression, vacuum, selection, damping.
- **RFL:** gold-green / structural amber — realized structure, lattice, observability.

However, this must be tested under color-vision deficiency simulation. Do not rely on hue alone. Use shapes, line styles, labels, and ordering.

### 7.3 Accessibility sources and doctrine

ColorBrewer provides color schemes designed by data type and includes colorblind-safe options. Scientific-colormap literature emphasizes perceptual uniformity and avoiding maps with false contrast or flat spots. Cividis was designed for accurate interpretation by viewers with and without red-green color vision deficiency, and CMasher provides scientific colormaps designed to be perceptually uniform and mostly color-vision-deficiency friendly.

**Practical rule:**

- Sequential data: use `viridis`, `cividis`, `batlow`, `mako`, or `cmasher` sequential alternatives.
- Diverging data: use perceptually balanced diverging maps; avoid red/green.
- Categorical triad roles: use hue plus shape/position labels.
- Print test: every figure must work in grayscale.

### 7.4 Avoid the rainbow trap

Rainbow/jet palettes are seductive but dangerous. They can introduce false boundaries and distort gradients. For scientific plots, use perceptually uniform maps unless there is a domain-specific reason not to.

## 8. Typography and layout system

### 8.1 General typography

Use a serious scientific style:

- Body: high-quality serif or LaTeX default modern serif.
- Math: STIX/Latin Modern/Libertinus/Computer Modern-compatible math.
- Figure labels: clean sans-serif.
- Tables: slightly smaller sans-serif or matched serif, but consistent.

Do not mix too many fonts.

### 8.2 Figure typography

- Axis labels: large enough to read when printed at one-column width.
- Panel labels: A, B, C in bold, top-left.
- Captions: explanatory, not decorative.
- Units: always in axis labels.
- Avoid tiny legends. Prefer direct labels.

### 8.3 PDF layout principles

- Main figures should be readable at one-column or two-column width.
- Use vector PDF/SVG for diagrams, line art, tables, and plots.
- Use high-resolution raster only for astronomical images, heatmaps with millions of points, and spectrogram images.
- Keep figure background transparent or white unless a dark plate is intentional.
- Dark-background plates should be rare and high-impact.

## 9. Production toolchain

### 9.1 Best reproducible workflow

Recommended stack:

1. **Data extraction and preprocessing:** Python scripts, pandas, numpy.
2. **Static plots:** Matplotlib; optional Plotly for Sankey, then export to SVG/PDF.
3. **Network/DAG:** Graphviz or networkx -> SVG/PDF.
4. **Tables:** LaTeX `booktabs`, or generate styled table figures where status visualization matters.
5. **Manuscript assembly:** Quarto or LaTeX; use BibTeX/Biber; keep all figures in `/figures`.
6. **Final PDF QA:** check fonts embedded, vector/raster output, line weights, grayscale readability, and citation/credit compliance.

Quarto is attractive because it can combine Markdown, citations, code, equations, cross-references, and PDF output while supporting reproducible scientific workflows. For the final physics-style preprint, LaTeX remains the safest end target, whether written directly or generated from Quarto.

## 10. Visual style: “bad ass” but scientific

### 10.1 What “bad ass” should mean

It should mean:

- high contrast;
- exact hierarchy;
- disciplined negative space;
- cinematic opening plates;
- crisp vector linework;
- strong multi-panel figures;
- well-designed tables;
- diagrams that reveal dependency order instantly.

It should not mean:

- neon everywhere;
- fake 3D bevels;
- AI-style glowing nodes without data;
- decorative cosmic backgrounds behind text;
- chartjunk;
- unreadable dark-mode figures;
- pseudo-scientific symbols as ornament.

### 10.2 Use “cinematic plates” only as separators

A powerful PDF could use 3–4 dark visual plates:

1. CMB / primordial field.
2. Cosmic web / large-scale structure.
3. Bifurcation / recursive scaling.
4. Boundary ledger / no-retune architecture.

But the main paper must still be readable as a technical manuscript.

### 10.3 Recommended visual mood

- Dark graphite / near black for section separators.
- Off-white paper background for core figures and tables.
- Sparse accent colors.
- Sharp linework.
- Dense information, but structured.
- Labels embedded near data, not hidden in legends.

## 14. Scientific caption doctrine

A figure caption should let the figure stand alone. It should include:

1. what is shown;
2. what data or model produced it;
3. which parameters or sources were used;
4. how to read the visual encoding;
5. the claim boundary;
6. external credit/license if needed.

### Bad caption

> Recursive structure of the universe.

### Good caption

> **Figure X. Source-coupled closure composition in Module R V3.** Bars show the fractional contribution of source channels to the standardized residual audit under the frozen Module G packet. QV entropy flow and recoil dominate the source-coupled closure, while CIF/CP and RFL observer/rebirth terms contribute smaller stabilizing channels. This figure reports internal closure structure only; it is not an external cosmological fit.

### Great caption

A great caption includes the above plus the exact parameters and where the source data lives.

## 15. How to avoid visual overclaiming

The visual system must not accidentally imply stronger evidence than the text permits.

### 15.1 Use badges for evidence class

Every module figure can carry a small badge:

- `DETERMINISTIC INTERNAL`
- `SOURCE-COUPLED AUDIT`
- `PROJECTION BRIDGE`
- `PROXY SCREEN`
- `EXTERNAL RUN REQUIRED`
- `BLOCKED CLAIM`

This makes the paper more credible.

### 15.2 Separate observation, simulation, and schematic

Use explicit labels:

- **Observation:** Planck CMB map, actual survey data.
- **Simulation:** cosmic web simulation.
- **Schematic:** original RFC diagrams.
- **Internal model output:** Module G/R/N etc.
- **External validation target:** public data not yet run.

Do not mix these in the same visual without labels.

### 15.3 Never use a beautiful image as proof

A cosmic web image can inspire, orient, and contextualize. It cannot validate RFC by visual resemblance. The paper must say that explicitly when needed.

## 18. Data visualization source principles

The public data-visualization literature and best practices converge on several principles:

- Visualizations should serve analytical tasks: comparison, trend, distribution, relationship, composition, or flow.
- Tables are better for exact lookup; charts are better for patterns and relationships.
- Color should encode meaning, not decoration.
- Perceptual uniformity matters for continuous fields.
- Accessibility matters: colorblind readers, grayscale printing, screen readers, and low-resolution screens.
- Captions matter; low-quality captions reduce comprehension.
- Reproducibility matters: figures should be generated from data/code when possible.

For RFC, this means the visuals should let a skeptical reader see the logic of the framework without accepting any metaphysical premise.
